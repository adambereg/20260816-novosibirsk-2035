# Technical MVP Spec — «Новосибирск-2035» v0.1

Статус: архитектурный Source of Truth для реализации v0.1.  
Дата фиксации: 2026-08-16.

Если обычное инженерное предпочтение противоречит этому документу, приоритет имеет этот документ.

## 1. Назначение

«Новосибирск-2035» — небольшой статический информационный сайт о будущем большого города и одновременно экспериментальный Markdown publishing pipeline.

MVP должен доказать, что GitHub может быть единым источником истины для кода и редакционного контента, а публикация не требует CMS, базы данных или backend.

## 2. Целевая архитектура

Единственная целевая цепочка сборки:

```text
Markdown → custom Node.js builder → static HTML/CSS → dist/ → Netlify
```

Ограничения:

- не использовать Astro или другой static-site framework;
- не использовать React, Next.js, Vue или Svelte;
- не использовать CMS, database или backend;
- не добавлять Telegram Bot или Mini App в v0.1;
- использовать минимум JavaScript на готовом сайте;
- сохранять совместимость с будущим Publisher через стабильный Markdown contract.

## 3. Источники истины

- код и контент хранятся в GitHub;
- статьи хранятся только как `content/articles/<slug>.md`;
- этот документ — архитектурный Source of Truth;
- `docs/CONTENT_CONTRACT.md` — Source of Truth для формата статьи;
- `dist/` является генерируемым артефактом и не редактируется вручную.

## 4. Обязательный publishing-сценарий

Реализация должна доказать, что:

1. существует работающий статический сайт;
2. статья хранится как `.md`;
3. build script автоматически обнаруживает Markdown-файлы;
4. Markdown превращается в статическую HTML-страницу;
5. опубликованная статья автоматически появляется в общем списке материалов;
6. статья автоматически появляется на главной, когда это предусмотрено редакционной логикой;
7. sitemap обновляется автоматически;
8. изменение статьи требует изменения только соответствующего `.md`;
9. добавление статьи не требует изменения исходного кода сайта;
10. `draft: true` исключает статью из production build.

## 5. Обязательные артефакты

Репозиторий должен содержать и поддерживать:

- `docs/MVP_SPEC.md`;
- `docs/CONTENT_CONTRACT.md`;
- `AGENTS.md`;
- `README.md`;
- `netlify.toml`;
- content validation;
- минимальные автоматические тесты;
- production static build в `dist/`;
- статическую главную страницу;
- общий список `/articles/`;
- отдельные страницы статей;
- страницу `/about/`;
- custom `404.html`;
- `sitemap.xml`;
- `robots.txt`;
- базовые SEO metadata.

Для проверки механизма достаточно двух-трёх representative Markdown articles; большой объём редакционного контента не входит в scope.

## 6. Редакционная логика v0.1

- Production build публикует только статьи с `draft: false`.
- `/articles/` содержит все опубликованные статьи в обратном хронологическом порядке.
- главная показывает до шести новейших опубликованных статей;
- новейшая опубликованная статья с `featured: true` становится главным материалом;
- если featured-материала нет, главным становится новейший опубликованный материал;
- sitemap включает статические страницы и каждую опубликованную статью;
- черновик не должен создавать HTML, ссылку на сайте или запись в sitemap.

Подробные поля и правила описаны в `docs/CONTENT_CONTRACT.md`.

## 7. Дизайн

Сайт должен выглядеть как небольшой современный editorial project о будущем большого города.

Приоритеты:

- сильная типографика;
- чистая композиция;
- хороший long-form reading experience;
- responsive layout;
- аккуратная мобильная версия;
- минимум JavaScript.

Не следует оформлять сайт как муниципальный портал, SaaS dashboard или перегруженный интерфейс.

## 8. Критерии готовности

Перед завершением должны успешно выполняться:

```bash
npm run check
npm run build
```

Ошибки content validation, тестов, production build и проверки `dist/` должны быть устранены. Scope после успешного MVP не расширяется без отдельного запроса.

## 9. Deployment

Netlify публикует каталог `dist/`, созданный командой `npm run build`. Подключение аккаунта и репозитория к Netlify выполняется вручную владельцем проекта.
